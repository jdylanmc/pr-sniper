# Intent: proof-of-concept

Proof of concept exists to buy real information cheaply. It takes a
spitballed idea, library, framework, engine, concept, loose phrase, or
directive and stress-tests it with real code so the team can learn what works,
what fails, what the edge cases are, what gaps need filling, and whether the
approach fits what we are building.

The prototype is usually throwaway. The learning is not. The skill should
frame the question being tested, build the smallest isolated prototype that can
answer it, run the prototype, and capture observations and human feedback in a
findings packet that discovery, specification, or implementation can use.

It must not turn prototype code into product code, silently persist artifacts
in the repository, use real secrets or personal data, create tickets or specs,
deploy, or overrun the agreed learning goal. Discovery may route here only when
a bounded prototype would answer a discovery question; discovery still owns
alignment, handoff, compaction, and next-cycle selection.
